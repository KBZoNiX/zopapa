1. Purpose & scope

This document specifies the observed functional behavior of the Zopapa line-following robot as implemented today, built directly from the firmware source (src/zopapa/zopapa.ino plus five companion files), its two vendored libraries (src/libraries/DRV8833, src/libraries/ATRSensors), and the two KiCad hardware projects in hardware/: the Rapiduino main controller board and the ATR-8A 8-channel sensor board. No design document existed in the repository prior to this one — everything here is inferred from code and schematic/BOM inspection, not from an author's stated intent.

Where a hardware net could not be traced pin-for-pin with certainty (component geometry only, no textual net label), the claim is marked as inferred rather than confirmed. Section 13 collects every such item plus behavioral discrepancies found between code, comments, and naming.

2. System overview

The robot is a two-wheel differential-drive platform that follows a black or white line using an 8-sensor reflectance array, correcting heading with a proportional–derivative control loop (labeled "PID" throughout the code and comments, though no integral term is implemented — see 7.3). An optional turbine/fan subsystem adds downforce at speed. Live tuning and telemetry run over a single UART shared by USB and an onboard Bluetooth header. A relay-feedback (Åström–Hägglund) routine can auto-compute the PD gains, which persist to EEPROM on operator command; sensor calibration also persists to EEPROM automatically, so the manual calibration sweep is only needed once per sensor/track setup rather than on every power-cycle.

3. Main PCB — Rapiduino

Two-layer board, 1.6 mm thickness, built around a through-hole-socketed Arduino Nano (A1). Motor drive is an off-board TB6612FNG carrier module (A2) rather than a bare IC on the PCB. Passive support is mostly 0805 SMD; connectors are 2.54 mm through-hole headers throughout.

4. Sensor PCB — ATR-8A

A dedicated 8-channel reflectance array using QRE1113GR phototransistor/IR-LED pairs (U1–U8), read as analog voltage dividers — not the digital RC-discharge timing scheme some QTR-style boards use. Each phototransistor has its own 47 kΩ pull-up feeding directly into one Arduino ADC channel. Only four 120 Ω resistors serve eight IR LEDs, consistent with the LEDs being wired in series pairs to share a single current-limiting resistor per pair. Two 0.1 µF caps decouple the board's local supply rail. All 10 signals (8 channels + VCC + GND) leave through a single header, CN1, matching the main board's J6.

R5 (1 kΩ) and R6 (2.2 kΩ) are unrelated to the driver: together they form a resistive divider that shifts the Nano's 5 V TX line down to ≈3.3 V (5 V × R6/(R5+R6) ≈ 3.44 V) for the Bluetooth module's RX input — see D0/D1 in the pin map above.

6.1 DRV8833 — motor driver library

A from-scratch library (v1.0, 2022-07-19) written to drive a DRV8833/TB6612-class dual H-bridge using only two Arduino pins per motor. Each instance owns two pins and defaults to SLOW_DECAY mode — motorIzq.mode()/motorDer.mode() are never called in the sketch, so this default is what actually runs. In SLOW_DECAY, speed(x) holds one pin HIGH (sets direction) and PWMs the other pin at duty 255 − |x| — a locked-antiphase drive, the inverse of a naive "one pin PWM, other pin LOW" scheme: x = 0 yields ~100% duty on the PWM pin (near-full braking torque at rest), while x = ±255 yields ~0% duty (free spin). stop() drives both pins HIGH (hard brake); free() drives both pins LOW (coast).

This is consistent with §5: a TB6612 module only behaves this way if its PWMA/PWMB/STBY lines are already held enabled, since the library never touches them — and on this board those three lines are hardwired directly to +5 V for exactly that reason.

6.2 ATRSensors — line sensor library

A modified, speed-optimized fork of Pololu's QTRSensors (public 2010 code, CC BY-SA 3.0 notice retained in the header), restricted to analog-only sensors. Two changes account for its performance: the ADC prescaler is dropped from the Arduino default of 128 to 32, and each sensor is read with a single sample instead of QTRSensors' 4-sample average. Per the library's own header comment, this cuts per-sensor read time from ~450 µs to ~45 µs, and readLine() over 4 sensors from ~2100 µs to ~250 µs. That speed-up is what makes reading all 8 channels fit comfortably inside the 2 ms LOOP_MS control period (§7.3, §11).

It also changes the original library's output scale: readLine() returns 100 units per sensor, not QTRSensors' 1000 — which is why zopapa.ino computes centro_de_linea = (N−1)×100/2 = 350 for the 8-sensor array rather than 3500. IR-LED brightness control from the original QTRSensors is disabled, consistent with the ATR-8A board having no LED-enable/dimming circuitry (§4).

7. Functional behavior

7.1 Operating states

StateValueMotorsTurbineSerial commands accepted
Stopped0OffOffFull command set
Running1PD steering activeOffP (stop) only
Running + Turbine2PD steering activeRamped, correction-proportionalP (stop) only

A short press of the pushbutton cycles Stopped → Running (or Running+Turbine, if DIP_SW3 reads LOW at the moment of the press) → Stopped. Holding the button ≥2 s does something else entirely, gated by DIP_SW4: with DIP_SW4 LOW it saves the current KP/KD/SPEED to EEPROM; with DIP_SW4 HIGH it instead runs a fresh sensor calibration sweep (same as the C serial command, §9). Neither path launches autotune itself — that only happens at boot, or via the T serial command. Both long-press branches set estado = 1 mid-hold as a deliberate trick: the button handler's post-release logic (if (estado != 0) estado = 0) then always resolves to Stopped on release, regardless of what state the robot was in before the hold started — so both long-press actions leave the robot Stopped afterward, never mid-drive.

7.2 Startup & calibration

On reset: if a valid sensor calibration is stored in EEPROM (§10), it loads directly and the boot continues immediately. Otherwise, a beep/LED intro is followed by a fixed 3-second manual calibration window (sensor bar min/max learning) during which the operator sweeps the array across the line — the result is then saved to EEPROM so the sweep isn't needed again next boot. The C serial command (§9) forces a fresh sweep on demand at any later point. If EEPROM_AUTOLOAD is set, saved KP/KD/SPEED also load from EEPROM (independently of the calibration data). If DIP_SW4 reads LOW, a 5-second window opens for a button press to launch autotune before falling through to normal Stopped state.

7.3 Steering control loop

Runs every LOOP_MS = 2 ms. Line position is read as centro_de_linea − Regleta.readLine(), where centro_de_linea = 350 for 8 sensors (range roughly −350…+350). Correction is:

correction = KP·position + KD·(position − last_position)

Clamped to ±MAX_CORRECTION (2×SPEED) and applied asymmetrically: whichever wheel needs to slow down is reduced by the correction magnitude, while the other wheel stays pinned at SPEED — it is not a symmetric add-to-one/subtract-from-other mix. Each wheel's resulting target then passes through DRV8833::speed() (§6.1), which realizes it as a locked-antiphase (slow-decay) drive rather than a simple one-pin-PWM/one-pin-LOW scheme.

Naming discrepancy The controller has proportional and derivative terms only — KP·position + KD·Δposition, no integral accumulator — yet is called "PID" throughout the code, comments, and the autotune routine.

7.4 Line-loss safety cutoff

If the reported position saturates at either extreme (line off both visible edges), a counter increments each loop; after MAX_CICLOS_SIN_DETECTAR = 100 consecutive cycles (~200 ms at the 2 ms loop rate) with no line detected, the robot auto-stops.

7.5 Turbine control

Active only in Running+Turbine. Target duty is map(abs(correction), 0, MAX_CORRECTION, MIN_SUCTION, MAX_SUCTION) — i.e. suction scales with how hard the robot is steering — ramped toward that target by RAMP_STEP=5 per cycle for a smooth response. MIN_SUCTION/MAX_SUCTION are 20/80 out of 255 (~8–31% duty); a source comment flags 128/255 (~50%, ~4 V) as the hardware ceiling not to exceed, which the configured range respects with margin.

8. Autotune subsystem

Implements the relay-feedback (Åström–Hägglund) method to derive PD gains from an induced, self-sustaining steering oscillation.

  1. Trigger. Either (a) at boot, if DIP_SW4 is LOW, a 5 s window opens for a button press to start it, or (b) any time via the T serial command.
  2. Excitation. Steering correction is forced to a fixed-amplitude square wave (d = 0.5×SPEED), flipping sign each time a peak in line position is detected, sustaining oscillation.
  3. Measurement. The first 3 peaks are discarded (settling); the next 6 peaks' amplitude (a) and period (Pu) are averaged.
  4. Gain calculation. Ultimate gain Ku = 4d / (π·a); Ziegler–Nichols PD rule gives Kp = 0.8·Ku, Kd = Ku·Pu/8, both scaled by a 0.9 safety factor before being installed into RAM.
  5. Persistence. New gains live in RAM only — nothing is written to EEPROM until the operator explicitly commits via the long-press gesture (§7.1) or the W serial command.
Comment vs. code mismatch The safety timeout constant is 2000 ms (2 s), but the adjacent source comment reads "25 s timeout". The 2 s value is what actually governs the abort.

9. Command interface (Serial / Bluetooth)

A single parser reads line-buffered text from the Nano's one hardware UART — physically shared between the USB programming port and the Bluetooth header (J5) at 9600 baud. The firmware has no way to distinguish which physical link a command arrived on.

10. Persistent storage — EEPROM layout

AddressSizeContent
01 bytePID init flag (1 = KP/KD/SPEED below are valid)
1–22 bytesCalibration magic marker (0xC1 0xB8 = calibration data below is valid)
44 bytes (float)KP

16–238 bytesSensor calibration minimums, one per channel

Why a 2-byte marker, not a single flag byte The PID flag at address 0 uses a plain == 1 check, matching the original design. The calibration flag deliberately doesn't: on the test hardware, address 1 already held 0x01 from data left over by a prior sketch, which would have made a single-byte check falsely report "valid" and load garbage as real sensor calibration. A 2-byte fixed marker makes that kind of accidental collision with pre-existing EEPROM content far less likely.

13. Assumptions & open items

  • Firmware — dead codeDIP_SW1 ("increase speed") and DIP_SW2 ("increase KP/KD") are wired and initialized as inputs but never read anywhere beyond pinMode() — the two switch positions currently do nothing.
  • Firmware — dead codedebug_macros.h defines DBG_PRINT macros gated on DEBUG==1, but the header is not #included by any .ino file.
  • NamingThe steering controller is P+D only (no integral term) despite being called "PID" throughout code, comments, and this repo's naming.
  • Comment vs. codeAutotune timeout comment says "25 s" next to a constant that is actually 2000 ms.
  • Command asymmetrySerial S (start) never enters Running+Turbine state, unlike the pushbutton path which honors DIP_SW3.
  • ProvenanceBoth vendored libraries (src/libraries/DRV8833, src/libraries/ATRSensors) are first-party code, not the SparkFun/Pololu libraries the same or similar names might suggest; ATRSensors is explicitly a modified, speed-optimized fork of Pololu's QTRSensors and retains its original CC BY-SA 3.0 notice.
  • UnresolvedExact Bluetooth module part number is not specified — J5 is a generic 4-pin header (VCC/GND/TX/RX assumed by convention).
  • UnresolvedNo revision, author, or date metadata found in either KiCad project — board revision history is not recoverable from the files present.
